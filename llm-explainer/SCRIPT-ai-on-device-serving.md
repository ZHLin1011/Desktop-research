# 第 12 期 · 端侧的推理服务（手机里的小厨房）

- 页面：`ai-on-device-serving.html`（白底，1080×1920，约 229 秒）
- 主线：接着第 10 期（云端推理服务）讲端侧。云端是「大饭店的后厨，同时伺候成千上万人」，端侧是「手机里的小厨房，只伺候你一个人，但灶台小、电有限、多个应用抢着用」。
- 结构：共用一份模型（系统级服务）→ 对照云端五站，端侧一次请求走哪几站 → 加载（冷启动 / 常驻 / 被请出内存）→ 多应用怎么排先后 → 电和热的天花板 → 借系统的还是自带模型（推理引擎）→ 搞不定就上云兜底 → 看端侧 AI 的四个问题。
- 颜色分工：入口 / 应用蓝，调度 / 内存青，模型 / 自带紫，GPU / 正常绿，加载 / 暖橙，风险红。
- 与前后期的分工：第 6 期讲「手机里的 AI 怎么跑起来」（内存、NPU、带宽、量化），本期讲「谁来安排」——服务层；第 10 期云端五站，本期用同一条线对照；第 11 期讲开发者调云端 API，本期讲开发者在端侧的两条路。

## 分镜

| 场景 | 画面 | 要点 |
|---|---|---|
| 01 云端是大饭店，端侧是小厨房 | 云端大饭店 + 两排人群 → 手机里的厨师帽与灶台 → 两个标签（只伺候你一个 / 灶台小、电有限、应用抢着用）→「怎么安排？」 | 云端伺候成千上万人，端侧只伺候你一个，但资源紧 |
| 02 一个模型，全手机共用 | 四个应用 → 各带一份 1.5 GB 模型，内存条被撑爆 → 系统里只放一份，四个应用都指向它 → 底座 + 摘要 / 改写 / 纠错小插件 → 苹果、安卓都在这么做 | 系统级公共服务；按任务换小插件 |
| 03 一次请求，走哪几站 | 上方云端五站（变淡）；下方端侧五站：提需求 → 排先后 → 加载（多出来的一站）→ 读题写答案 → 送回 | 云端愁人太多，端侧愁地方太小 |
| 04 模型在不在内存里 | 存储里的模型文件 → 搬进内存（冷启动，计时）→ 留在内存里（常驻）→ 相机、微信、游戏挤进来，模型被请出 → 两根条：第一次好几秒，后面秒回 | 冷启动 / 常驻 / 被内存回收 |
| 05 应用多了，谁先用 | 三张任务单（输入法续写、相册整理、录音摘要）+ 灶台；前台任务优先开火；后台等充电、锁屏；单人不拼车 | 前台优先、后台让路；端侧通常不需要拼车 |
| 06 小厨房的天花板：电和热 | 电池下降、温度计上升 → 字速曲线在「过热，芯片降速」处下台阶 → 三个应对：短任务快做、长任务分段、省电换小模型 | 持续运行发热降频 |
| 07 借系统的，还是自带模型 | 左卡：应用 A / B 指向系统模型（省空间、省内存、更新有人管；不能自己挑）；右卡：应用里装模型 + 推理引擎（想用哪个都行；包变大、内存自己扛）；引擎名称示例 | 两条路的取舍；多数应用借系统的 |
| 08 小厨房搞不定，就上云 | 需求 → 判断 → 端侧（当场办：润色、总结短信）/ 云端（长文章、最新消息、难推理）；四条规则；「你几乎感觉不到」 | 混合路由 |
| 09 看端侧 AI，问这四件事 | 手机 →「断网能不能用 / 第一次慢不慢 / 连续烫不烫 / 数据出不出手机」→ 云端比后厨大，端侧比小厨房安排得好 | 收束 |

完整逐句旁白在 `ai-on-device-serving.html` 的 `SCENES` 中（TTS 逐词时间戳生成，画面按节拍对齐）。

## 概念与说法依据

| 画面 / 旁白 | 依据 | 备注 |
|---|---|---|
| 一份 1.5 GB、手机内存撑爆 | 第 6 期：30 亿参数模型压缩（约 4 位）后约 1.5 GB；手机内存常见 8–16 GB，且与系统、微信、相机共用 | 「四个 6 GB」为算术示意 |
| 系统统一放一份，应用通过接口使用 | Apple 的 Foundation Models 框架（WWDC25）向应用开放系统自带的端侧模型；Android 的 AICore 作为系统服务托管 Gemini Nano，应用经 ML Kit GenAI 等接口调用 | 旁白只说「苹果和安卓都在往这个方向走」 |
| 按任务换小插件 | 常见做法是在同一个底座上按任务加载 LoRA 适配器；Apple 的基础模型技术报告提到按任务加载适配器 | 摘要 / 改写 / 纠错为示意 |
| 冷启动要等好几秒、常驻秒回 | 模型文件需从闪存读入内存并完成初始化，量级从一秒到数秒不等，随机型、模型大小和是否已缓存而异；已常驻则免去这一步 | 量级，非固定值 |
| 内存一紧，模型被请出去 | iOS 与 Android 都会在内存紧张时回收后台进程和缓存（如 iOS 的 jetsam、Android 的 lmkd）；被回收的模型下次需重新载入 | 「游戏之后第一次用 AI 慢」是常见体验 |
| 前台优先，后台等充电、锁屏 | 两大系统的后台任务机制都支持「充电中、空闲时」才运行的约束（如 iOS BGProcessingTask、Android WorkManager 的约束条件）；相册索引、批量整理常这样做 | |
| 端侧不用拼车 | 云端靠连续批处理把多人请求拼车（第 10 期）；端侧通常只有一个用户，批大小接近 1，主要瓶颈是内存带宽（第 6 期） | 「通常」；多任务并发时仍会排队 |
| 过热降速、字越蹦越慢 | 手机和平板有温控机制，持续高负载会降频；图中曲线为示意，不是实测数据 | 各机型表现不同 |
| 推理引擎示例 | llama.cpp（开源）、Core ML（苹果）、LiteRT（谷歌，原 TensorFlow Lite）、MNN（阿里开源）都是端侧推理引擎 | 仅作示例，不含排序或推荐 |
| 简单的当场办，复杂的转云端 | 混合路由是常见架构：苹果把更复杂的请求交给其私有云，谷歌与多数手机厂商也有端云协同；路由因素包括任务难度、网络、电量、隐私设置 | 具体规则各家不同 |
| 四个问题 | 总结性提问，对应本期的加载、散热、联网兜底与隐私特性 | |
